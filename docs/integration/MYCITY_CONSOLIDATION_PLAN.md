# MyCity interface consolidation and backend connection

## Decision and current state (September 28, 2026)

The interface being edited at `/mycity#/coordinator/home` is the visual source of truth. Its source is `experiments/volunteer-coordination/`. Preserve its layout, typography, interactions, and issuer/volunteer navigation while connecting real data. The existing Next.js service layer and database schema are the backend source of truth. The older `/aesthetic-lab` pages are a reference implementation of connected workflows, not a second design to maintain.

This does **not** require merging two unrelated repositories. `codex/prototype-platform-integration` descends from `branch1/CSV1.0` (merge base `63b3e9b`) and already contains the aesthetic lab backend. The current worktree has substantial uncommitted UI changes and new assets. The separate `Progress-aesthetic-lab` worktree also has four uncommitted page/style changes. Account for both sets of changes before any branch merge; do not reset or clean either worktree.

Today, `/mycity` requires a session but serves the prototype's browser-local state. Its response deliberately uses `connect-src 'none'; form-action 'none'`. The account menu sends Settings to `/aesthetic-lab/settings`, a connected page with the old shell. The launcher on port 4320 uses `.integration-preview/`, a separate local database. None of the edits made inside `/mycity` are persisted to the platform database. `vercel.json` runs `db:migrate:schema` during a deployment build, so preview and production database credentials must stay separate.

## One-route outcome

Use `/mycity` as the integration route and later make it the authenticated issuer and volunteer entrypoint. Keep `/aesthetic-lab` and older `/issuer` routes reachable while their workflows are being replaced, but remove them from the primary navigation. Once parity is verified, redirect old links to the corresponding MyCity screen and retire only unused UI code. Keep domain services, schema, historical records, upload handlers, and public URLs that are still referenced.

The app must use the signed-in session's user, organization, delegation, and active city. The prototype's persona switch, localStorage mutations, sample organizations, reset control, and browser-only waiver files cannot operate as live account data. Replace them with real reads and mutations **per complete workflow**. Preserve the prototype views/CSS as the presentation contract; an adapter or isolated React translation may be used, but do not layer more aesthetic-lab CSS overrides onto them.

## Rules for each connected slice

- A workflow is done only when its initial read, mutation, validation, loading/error/empty states, authorization, persistence after refresh, and both issuer/volunteer consequences work with the isolated database.
- Keep prototype state only for explicitly labeled demo fixtures while a screen is unconnected. Do not combine demo IDs with real database IDs in one workflow or display simulated confirmations as live outcomes.
- Add schema changes forward-only, with a tested migration and existing-row defaults. Do not replace the database or run an experimental build/migration using production credentials.
- Before deleting a route/component, search for inbound links, redirects, server actions, public URLs, and tests; remove only UI that has a connected MyCity replacement. Historical data and ledger behavior are outside visual cleanup.

## Immediate acceptance milestone

The first reviewable increment is the real MyCity shell and Organization Settings: signed-in organization and city appear in the current header, the Settings menu stays in that design, edits survive refresh in `.integration-preview/application.db`, non-owners cannot change owner-only fields, and the old settings page is no longer reached from the MyCity menu. This establishes the adapter, permissions, routing and visual pattern for the remaining pages without risking the live deployment.

### September 29 integration result

The first increment now loads authenticated organization and city context through `/api/mycity/context`. The header lists only the signed-in person's available volunteer and issuer identities; `/api/mycity/identity` switches among those existing delegations without leaving MyCity. The issuer avatar menu opens `#/coordinator/settings` in the current shell. That form saves through `/api/mycity/organization-settings`, which uses the existing owner-only `updateOrganizationIdentity` service and compares the browser Origin with the request Host. The prototype's remaining screens are still explicitly labeled sample data.

In the isolated preview, the owner saved a location edit, refreshed and saw the persisted value, then restored the original location. An owner of another organization was denied by the service without changing the target organization's name. An unauthenticated request to each endpoint returned 401. TypeScript, the production build, the frontend asset check and all 106 prototype tests passed. A dedicated non-owner staff browser fixture remains to be exercised before production cutover.

The integration branch now has three dedicated Turso databases: `citysync-mycity-preview-core`, `citysync-mycity-preview-berkeley-ledger`, and `citysync-mycity-preview-mexico-city-ledger`. The full migration and demo seed completed against only those databases. Thirteen Vercel variables, including database credentials, `AUTH_SECRET`, `CITYSYNC_COORDINATION_UI=integrated`, stub email/anchoring, and local file storage, are scoped to `codex/prototype-platform-integration` in Preview. The first deployment without credentials failed as intended; a redeploy after configuration reached Ready. The application and migration fail clearly on Vercel if `DATABASE_URL` is absent, and a city connection fails if its URL is absent; neither can silently use a local SQLite fallback. The current local `.integration-preview/` database also remains isolated from production.
